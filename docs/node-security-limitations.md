# ward-node security limitations

Status: living document. It is the security statement for the `ward-node` substrate as
shipped at this revision (protocol 1.3 with its additive revisions, ADR-0030 steps 1–13,
#332 slices 5–10 and stage 2, the first single-node slice of #260, the action
channel of ADR-0031, #404, the brokered credentials of ADR-0034, the first node slice
of #267, the approval holds of ADR-0035, #415, and the agent adapters hosted on admitted
workloads of ADR-0036, #279, with the operator's `ward-agent` shim and relay of ADR-0037,
#424, in every attempt behind an egress proxy since #267, and the mutual-TLS transport of ADR-0038, the remote-transport slice of #262, with
its client-key revocation and reload on `SIGHUP`): what the
node enforces, what it does not, and what each gap means for an external control plane.
The contract is [node-integration.md](node-integration.md), the proof of what is claimed
here is [node-acceptance.md](node-acceptance.md), and what CI checks on every change is
[node-release-readiness.md](node-release-readiness.md). The project-wide statements this
document refines are [threat-model.md](threat-model.md) (§3.1, fleet trust) and
[security-model.md](security-model.md) (§2, non-guarantees).

A limitation listed here is not a bug. It is a boundary of the current implementation
that a control-plane author has to design around, stated so that nobody has to read the
code to find it.

## 1. Trust model in one page

- **The node is the enforcement authority on its host**
  ([ADR-0029](decisions/ADR-0029-product-split-fleet-trust-boundaries.md)). It decides
  whether a task runs and owns its workspace, spawn, budget, interventions, records and
  evidence. Nothing the control plane sends is executed on the control plane's word
  alone.
- **The control plane signs; the node verifies.** Authority reaches the node as one
  admission envelope (binding, agent, node audience, session, lease and lineage, argv,
  capability manifest, snapshot id, mandatory wall-clock budget, validity window,
  per-task version) with a detached Ed25519 signature over the exact bytes sent
  (node-integration.md §7). The node accepts a signature only from a key in its trust
  store, and only for the one principal that key is bound to (§2.2); it then checks
  audience, validity, version, lineage contraction, revocation and the manifest, in the
  order of §8.1, before anything is materialised.
- **The socket proves nothing.** Reaching the Unix socket gives a peer the ability to
  `create`, `inspect` and send verbs; it gives no authority to run anything. Every
  execution verb needs an admitted envelope, and `admit` needs a trusted signature.
  Conversely, the socket is mode 0600 in a 0700 directory, so by default only the
  node's own uid can reach it at all; an operator who shares it with a group
  (`--client-group`, mode 0660) names the uids it serves (`--client-uid`), and the node
  checks every connection's peer credentials before it reads a byte, closing any other
  peer without a response (§2.1, §3, §11.1). Being served is not authority either.
- **The workload is hostile.** It runs in a bubblewrap sandbox with its workspace as the
  only writable host path, no network but loopback (or, on a node started with
  `--network-allowlist`, the attempt's own egress proxy allowing exactly its manifest's
  hosts), and an environment the node constructs from nothing (§9). The node's state, trust store, evidence logs, stored
  results and socket are never visible to it. What comes back out is only what the
  manifest declared and only after the workload is gone: on a node started with
  `--output-return`, the head of its stdout and stderr and the declared workspace files,
  read without following anything outside the workspace (§6.6).
- **Evidence is the node's.** One append-only, hash-chained `ward-events` log per
  attempt, written by the node alone, outside the sandbox's reach (§6.5). It records
  what the node did and observed, never workload output itself: a returned result is
  recorded by its counts and digests (`NodeAttemptOutputCollected`), so a control plane
  can bind what it received to the sealed log.

## 2. What is enforced

Each row names the mechanism and where it is proven. "Acceptance" is a case of
[node-acceptance.md](node-acceptance.md) §2; "unit" means `ward-node`'s own tests, run
under the merge gate.

## 3. What is not enforced

Each limitation names its impact for an external control plane, what an operator can do
today, and the issue that closes it. "No issue yet" means exactly that: the gap is
known and recorded here, and no child issue has been opened for it at this revision.

### 3.1 Transport and trust bootstrap

| Limitation | Impact | Mitigation today | Closed by |
| --- | --- | --- | --- |
| **Remote transport is mutual TLS with operator-provisioned identities.** Besides its Unix socket, a node started with `--listen-tls` serves the protocol over TLS 1.3 with client certificates (§2 above, §3). Its certificate, key, client CA, pins and list of revoked client keys are files and flags the operator provisions; the files are reloaded on `SIGHUP`, the pins only by a restart. There is no enrolment, no attestation of what runs behind a key, no certificate revocation list or OCSP, no propagation of a revoked key to other nodes, no revocation list for node keys on the shipped client (it pins one), and handshakes are reported on stderr (the journal under a service manager), not recorded durably. | A control plane on another host is authenticated and the channel is confidential. A stolen client key is accepted until the operator adds it to the node's revocation list and sends `SIGHUP` (no restart, no attempt lost), or until its certificate expires; until then, and on every node whose list was not updated, a stolen key can `create`, `inspect`, `stop`, `revoke`, `answer` and read results, never `admit` (that needs the issuer key). Whether a node runs what it should is not proven by its certificate. Without `--listen-tls`, a control plane elsewhere still brings its own channel to the host, unauthenticated by the node. | Start every node with an empty `--tls-client-revoked` list so a revocation needs no restart, and push a revoked key to every node that serves it; issue short-lived client certificates; pin the control plane's keys when the client CA certifies anything else; open the port to the control plane's network only; keep the issuer key on the control plane and pre-sign; keep the journal (node-integration-guide.md §3.1). | [#262](https://github.com/hexrift/WardOS/issues/262) (enrolment, attestation, CRLs and propagation, a durable handshake record; ADR-0038 What remains) |
| **Same-uid co-location by default.** The socket (0600), state directory (0700) and task root (0700) are reachable only by the node's uid unless the operator lists the uids the node serves (`--client-uid`) and the group that may connect (`--client-group`: socket 0660 in a 0750 group-owned directory); the node then checks every connection's peer credentials before reading a byte (§2.1, §3, §11.1). | With the default, a process that can talk to the node can also read and edit the node's state files, evidence logs and workspaces: a compromised client on the host is a compromised node on that host. With listed client uids, a compromised client can still `create`, `inspect` and send every verb, but cannot read or edit the node's state, records, logs or workspaces, and the issuer key still gates admission: the allowlist decides who may speak, the trust store decides whose authority counts. | Give the node its own system user with nothing else in it; run the adapter as a second user, listed with `--client-uid` and a member of the `--client-group` group (node-integration-guide.md §3); keep the issuer key elsewhere so the host cannot mint authority for any node. | The local peer-credential check is in place at this revision (the first slice of [#262](https://github.com/hexrift/WardOS/issues/262)); the remote path, where no uid exists to check, authenticates by client certificate instead (ADR-0038) |
| **Manual trust-store bootstrap.** The operator writes `--trusted-issuers` by hand (§2.2). There is no enrolment, no attestation of the node and no node identity beyond the `--node-id` the operator chose and, on a node started with `--listen-tls`, the certificate the operator provisioned for it (ADR-0038). | Over the socket, the control plane cannot verify which node it is talking to beyond the audience id the envelope names and the socket it reached; over TLS it knows which key answered, not what runs behind it. A node id is a label, not a credential, and nothing binds it to the node's certificate. | Treat the host's own identity (its SSH host key, its image) as the node's identity for now; keep one `node_…` per host and never reuse it; issue each node's certificate for a name the control plane maps to that `node_…`, or pin each node's key. | [#262](https://github.com/hexrift/WardOS/issues/262) |
| **Issuer key rotation needs a restart.** The trust store, like the TLS pins, is read once at start; a change to either is a node restart (§2.2), which turns every running attempt into `exited`/`unknown` (§6.4). The TLS certificate, key, client CA and client revocation list are reloaded on `SIGHUP` instead (node-integration.md §2.1). | Rotating or removing an issuer key, or changing the pins, costs every attempt in flight on that node; rotating a TLS identity or revoking a client key does not. | Bind the new key before the old one is retired (several keys per principal are allowed), drain the node (stop admitting, wait for attempts to end, seal), then restart with the old key removed. | [#262](https://github.com/hexrift/WardOS/issues/262) |
| **Revocation is local.** `revoke` and `revocations.json` are per node; there is no propagation to other nodes or acknowledgement to the control plane beyond the verb's answer (§2.5). | A lease revoked on one node is still admissible on another node that trusts the same key until it expires or is revoked there too. | Keep lease lifetimes short (expiry is the fallback bound), and revoke on every node a lease could reach. | [#262](https://github.com/hexrift/WardOS/issues/262) |
| **No clock-skew policy for envelopes.** Envelope and lease validity is judged at the node clock at `admit` and `start` (§10); the contract says to leave margin, and nothing measures or bounds the skew. Certificates on the TLS listener do have one: valid give or take 60 seconds at the verifier's clock, on both sides (ADR-0038). | A node whose clock is wrong refuses valid envelopes (`authority_denied`, `lease_expired`) or accepts ones the control plane considers expired; with a clock off by more than a minute, TLS handshakes fail `certificate expired` or `not valid yet` on one side or the other. | Run NTP on the node host; issue envelopes with a margin on both ends and short lifetimes; treat a refusal as a signal to check clocks. | [#262](https://github.com/hexrift/WardOS/issues/262) names the envelope policy; no test of envelope skew exists (node-acceptance.md §4); the certificate allowance is unit-tested (`tls`) |

### 3.2 What a workload can and cannot do

| Limitation | Impact | Mitigation today | Closed by |
| --- | --- | --- | --- |
| **Egress through the proxy socket only, and only when enabled.** A `network.custom` manifest is honoured only on a node started with `--network-allowlist` (§2.1), and then as HTTP(S) through the attempt's proxy at `/run/ward/proxy.sock`: `CONNECT` tunnels and absolute-URI HTTP forwarding, host-level patterns, no loopback relay and no `HTTP_PROXY` inside the sandbox except on a node started with `--agent-shim`, where every attempt behind a proxy has both (§6.8, §6.10, ADR-0037 §7); a credential only on a node started with `--credentials`, and only on its own route (§6.8, §9). | On a node without the shim a workload must speak to the Unix socket itself, and a tool that only honours `HTTP_PROXY` cannot use the proxy. On a node with it, an attempt behind a proxy runs under the shim's Landlock ruleset and seccomp filter, so a plain workload that writes outside `/work`, `/env`, `/tmp` and `/home/agent` fails there. Patterns name hosts, not paths or methods. Only the configured services authenticate, and only through their routes. | Ask the operator for `--agent-shim`; or give the workload a client that can address a Unix-socket proxy, or keep dependencies in the snapshot (`ward-node snapshot import`, §2.4) and do the rest on the control plane's side. | [#424](https://github.com/hexrift/WardOS/issues/424) relays for hosted adapters, [#267](https://github.com/hexrift/WardOS/issues/267) for every attempt behind a proxy (the shim ships in the node tarball since [#427](https://github.com/hexrift/WardOS/issues/427)); the capability document does not say whether a node relays |
| **Result return is bounded, declared and only when enabled.** On a node started with `--output-return`, `result` returns the first 1 MiB of each of stdout and stderr (the head, never the tail), and only the files the manifest declared by exact relative path, up to 8 MiB of content in all with digests for the rest (§6.6, §7.5). Nothing streams while the attempt runs, there are no globs or directories, and the workspace is not exported: `snapshots.read` and `snapshots.diff` are `false` (§5). A node without the flag refuses the grant `unsupported_grant`. | A control plane gets what it asked for, bounded, after the attempt ended, bound to the sealed log by the digests of `NodeAttemptOutputCollected`; it does not get a live feed, a workspace diff or files it did not name. A workload the node lost track of, or an attempt the node restarted over, has no result (`resource_unavailable`). | Declare the files the workload is expected to write, and have it write a summary file for anything else; keep the exit status the verdict. For the rest of the workspace, read it on the host as the node's uid, as before. | No issue yet for a workspace export as a content-addressed snapshot (`snapshots.read`, `snapshots.diff`) or for streamed output |
| **Approvals are enforced only as a hold on a host or a credential.** On a node started with `--action-channel` and `--approval-hold` (and `--network-allowlist`), a manifest's `hold` names hosts of its `network.custom` and services of its `credentials`; the attempt's proxy refuses each `403` by name until the control plane's approval of the request the node opened for it on first use is recorded, and keeps it refused after a denial, an expiry or the attempt's end (§6.9, ADR-0035). Nothing else is held: an approval the workload asks for itself is still a statement the node records and relays (§6.7), and a file the workload writes or a command it runs is never gated by the node. A release lasts for the rest of the attempt (a later request for the capability is not asked again); a host is held by name, so another allowlisted name for the same address is not held; a hold opens only on a request the proxy sees, so it says nothing about traffic that has no path anyway. The hold's refusals travel the proxy's bounded verdict queue and are appended after the workload is answered (what the node releases and what it lists is always recorded first). An `answer` is authorised by the exact binding on the node's socket, not by a per-answer issuer signature, and its applied operation ids do not survive a node restart (a replay is then `invalid_state`; the log holds what was answered). `stream` is still `unsupported_operation`. | A control plane can make a human's yes a precondition the node checks before an agent reaches a held host or uses a held credential, with the request, the answer and every refusal in the sealed log, and a hostile workload cannot open, word or answer that request. It cannot gate anything else through the node, and cannot withdraw a release before the attempt ends. | Hold every host and credential an irreversible step needs; for anything else, treat an approval as advice to a workload you trust to wait for it and do the gated work on the control plane's side; keep budgets short where a release must not outlive one step; check the log's `NodeActionAnswered` records against what you answered. | [#262](https://github.com/hexrift/WardOS/issues/262) for per-answer authentication; no issue yet for holds on paths, commands or methods, one-shot releases or withdrawing a release before the attempt ends |
| **Credentials are brokered narrowly, and only when the operator configured them.** On a node started with `--network-allowlist` and `--credentials`, a `credentials` grant gets a lease for a service the operator configured, injected by the attempt's proxy as one header on plain-HTTP requests to `/<service>/…`, forwarded over TLS to that service's one upstream (§6.8). There is no other delivery: no credential is ever materialised in the sandbox (no short-lived token file or variable, ADR-0008's delivery B), none reaches a `CONNECT` tunnel, SSH, a Git remote other than a route's gateway URL (`http://127.0.0.1:3128/<service>/<repo>.git` through the shim's relay, credential-broker.md §8.1) or a registry protocol that is not plain HTTP on a route; the route sends the leased value behind the configured prefix and computes no encoding, so an upstream that accepts only HTTP Basic or its own tokens needs the provider to hold the value in that form (a static KV secret, not revocable at the source); and the capability document says whether a node brokers credentials but not which services. A provider outage, or a renewal that fails, is visible in the evidence log (`CredentialDenied`) and to the workload as a `403`, not over the socket. A lease the provider cannot revoke at the source (KV) ends with its route; one whose revocation the provider does not confirm, or that a killed node left and a restarted node cannot revoke, ends at its own TTL, which the attempt's budget bounds. The provider's revocation handle (never the value) is on disk beside the workspace while the lease lives. Credentials are not held across a pause by anything but the budget. | A control plane can let an agent call one authenticated HTTP service without ever holding its secret, and knows the credential dies with the attempt; a tool that needs a token in its own hands, or a protocol other than HTTP on a route, still cannot authenticate. | Configure one service per upstream the workload needs, with the narrowest role, paths and `max_ttl_secs`; read the attempt's evidence log for `CredentialDenied` before trusting a run; keep the node's provider token scoped to the roles the services use. | [#267](https://github.com/hexrift/WardOS/issues/267): delivery B, cloud STS backends, advertising the configured services, dedicated node credential record kinds, re-issuing a lease after a renewal fails |
| **A hosted agent adapter is equipped only with the operator's shim.** On a node started with `--agent-adapter` and without `--agent-shim`, Claude Code gets its settings and a hook socket but no `ward-agent` shim, so the hook command its settings wire (`/run/ward/ward-agent hook`) is absent, and no relay or base URL for its model API. With `--agent-shim` (ADR-0037) the hooks run and, behind an egress proxy, the provider's base URL points at the shim's relay for a provider the manifest grants a credential for; the capability document does not say which a node does, and the shim is the operator's to name: the node tarball carries it (#427) and node-integration-guide.md §1 installs it beside `ward-node`, but a node started without `--agent-shim` binds none. A hook answer is `allow` for every line: steering, recorded, never enforcement; a `PermissionRequest` is not bridged onto the action channel. The binding's runtime and model are what the adapter declares and the argv requests, not verified (§6.10, ADR-0036). | A control plane can rely on the node's enforcement and evidence for any adapter, and on agent-origin claims as the agent's account; it can run a real Claude Code or Codex session against its model only on a node whose operator named a shim and under a manifest granting the provider's credential, and it cannot gate a tool call on a hook answer. | Ask the operator for `--agent-shim`, or run runtimes that speak the contract's hook lines and the proxy socket themselves; enforce approvals with a hold (§6.9); read the binding as metadata. | [#279](https://github.com/hexrift/WardOS/issues/279), [#424](https://github.com/hexrift/WardOS/issues/424) (follow-ups: the relay in the capability document, a real-runtime CI run; the shim ships in the node tarball since [#427](https://github.com/hexrift/WardOS/issues/427)) |
| **Limits only on a node with a delegated cgroup, and never on disk.** Without `--cgroup-root` there is still no CPU, memory or pid limit on a workload, only its wall-clock budget, and a `resources` grant is refused. With it, CPU, memory (tmpfs writes included) and pids are bounded per attempt when the manifest asks and the host offers the controller (§7.5, §9), but nothing bounds the disk a workload writes under its workspace, nor its I/O bandwidth; requested limits are enforced, not reserved (the node does not refuse a start because the limits of running attempts add up past the host), and an attempt whose manifest asks for no limit runs unlimited (measured, not bounded). On a host with swap and no swap accounting (`memory.swap.max` absent) swapped-out pages escape `memory.max`. | Without the flag a workload can exhaust the host's memory, pids or disk for the length of its budget, as before. With it, a control plane that asks for limits gets them enforced by the kernel on the whole tree; disk under the task root stays the operator's. | Delegate a cgroup to the node and have the control plane always send `resources`; keep `--memory-floor` and `--disk-floor` set; put the task root on its own filesystem (with a quota); without a delegated cgroup, run the node under a service manager with limits on its unit (systemd `MemoryMax=`, `TasksMax=`), which bound every workload collectively. | [#260](https://github.com/hexrift/WardOS/issues/260) (disk and I/O limits, reservations and oversubscription policy, verifier/agent separation) |
| **Sandbox-private writable root.** The sandbox's `/` and the mount-point directories bubblewrap creates (`/etc`) are writable tmpfs inside the sandbox; the bound system directories are read-only (node-acceptance.md §5). Nothing written there reaches the host. | None for the host. A workload that assumes `/` is read-only (as a hardening check) will find it is not. | None needed for confidentiality or integrity; the memory impact is the row above. | No issue yet (an observation, not a hole; a read-only root would be a `ward-launch` change) |
| **The die-with-parent window.** bubblewrap's `--die-with-parent` takes a sandbox down with the node, except in the brief window between the spawn and the moment the just-spawned `bwrap` arms it; the node's restart recovery kills the tree rooted at the recorded host process only once that pid is recorded (§6.4). | A node killed in that window can leave a workload running with no budget enforcement, because the reaper died with the node. The attempt still recovers as `exited`/`unknown` and is never re-run. On a node started with `--cgroup-root` the window is narrower: whatever a reaped attempt left in its cgroup is killed (`cgroup.kill`), and a restarted node kills every attempt cgroup a previous run left behind before it serves; a node that is killed and not restarted still leaves the orphan running until it is. | Run the node under a service manager whose unit kills its whole cgroup on stop (systemd's default `KillMode=control-group`), so no orphan survives a unit restart, and give it a delegated cgroup root. | The per-attempt cgroup of [#260](https://github.com/hexrift/WardOS/issues/260) is in place behind `--cgroup-root`; no issue yet for killing an orphan without a restart |
| **Not an escape suite.** The isolation case is a contract check of what the sandbox denies to an ordinary workload (node-acceptance.md §4). Kernel privilege escalation from an unprivileged user namespace is a residual risk the project states publicly (threat-model.md §9). | A working kernel exploit defeats the boundary. | What the project does for every sandbox: a current kernel, no capabilities, no devices; `ward selftest`'s hostile probes on the session path. | [#263](https://github.com/hexrift/WardOS/issues/263) for a microVM tier |

### 3.3 Receipts, evidence and operations

| Limitation | Impact | Mitigation today | Closed by |
| --- | --- | --- | --- |
| **The receipt is not bound to the evidence head.** `inspect` reports the outcome; the protocol carries neither the log nor its sealed head (§6.5, §9). | Over the socket alone a control plane cannot tie the outcome it reads to the evidence that backs it; the binding exists only on the host. | Give the adapter `task_root` (§11.4): the report's `evidence_head` is the sealed `HEAD` the driver verified against the log, and `cause` is read from the log. Archive the log with the report. | No issue yet (an `inspect` or `seal` answer carrying the sealed head) |
| **Receipts are lost on replacement and eviction.** A new attempt replaces the old one's receipt; an evicted sealed task reads `task_not_found` (§9, §10). | Read the outcome before you retry or before the registry fills; after that, only the evidence log holds it. | Seal each finished task once its outcome is read; keep the logs (the node never deletes them). | Working as designed; no change planned |
| **Retention is the operator's.** Workspaces and evidence logs are never removed by the node (§6.5, §10). | Disk under the task root grows with every attempt until the operator reclaims it. | Reclaim out of band, only for attempt ids that will never be sent again, after the logs are archived. | Working as designed; no change planned |
| **One node, one process, one request at a time; no queue, no priority.** Connections are served serially; a slow `start` delays every other client for as long as it runs (§3). With `--max-running` the node bounds how many attempts execute at once and refuses a `start` past it `capacity_exhausted`, but it keeps no queue: there is no priority, no fairness between control planes and no starvation guard, and nothing separates verifier workloads from agent workloads. Without the flag it bounds nothing. | Throughput is bounded by the slowest verb in flight; a control plane needs its own queue (its `ready` tasks), retries a refused `start` once an attempt has ended, and must not treat a slow answer as a lost one. | Give verbs the timeouts §11.1 names; drive one node from one place; set `--max-running` to what the host can carry and read `scheduling` before starting; the reference Node.js client sends the same `start` again with a bounded backoff and reads `scheduling` before each wait ([node-integration-from-nodejs.md](node-integration-from-nodejs.md) §7.6). | [#260](https://github.com/hexrift/WardOS/issues/260) (a node-side queue with priority and fairness, a separate verifier bound) |
| **Concurrency is tested at 25, enforcement only where a cgroup is delegated.** The capacity acceptance runs 25 CPU-burning sandboxes at once on one node and checks every request is answered within 2 s (node-acceptance.md §2.4); the registry, pause and state-file bounds are unit-tested. CI's runner delegates no cgroup to the tests, so there the case that proves the kernel holds a workload at its pids, memory and CPU limits skips, and the cgroup path is proven by unit tests that run a real attempt in a cgroup only on a host with a writable cgroup2 directory. Memory pressure on the host is not generated by the suite, and single-attempt latency is not regression-gated. | How the node behaves with hundreds of attempts, under host memory pressure, or on a host whose kernel lacks a controller, is not measured by CI. | Keep the registry well under 1 024 tasks by sealing promptly; run `scripts/acceptance/node.sh` on your own host with `WARD_NODE_CGROUP_ROOT` (or as root) and `WARD_REQUIRE_CGROUP=1` before relying on limits; measure before relying on a figure. | [#260](https://github.com/hexrift/WardOS/issues/260) (a delegated cgroup in CI, memory-pressure and latency gates) |
| **No TamperWard verdict.** The node says what it did; whether a result is certified is the control plane's decision (ADR-0029). | A `completed` receipt is a report that the workload exited 0 within its budget, not a verification. | Run verification as its own attempt whose exit status is the verdict, and certify on the control plane. | Working as designed (ADR-0029 non-goals) |
| **The node artifact is not signed itself; it is checksum-bound to the signed release manifest.** `ward-node`, `ward-node-adapter` and the `ward-agent` shim ship in every release's node tarball, `ward-node-<node version>-<arch>-linux.tar.gz` with its `.sha256` ([node-release-readiness.md](node-release-readiness.md) §2). The release manifest records the tarball's digest and is signed keyless by the release workflow on the release tag ([release-manifest.md](release-manifest.md)), so a verified manifest proves which workflow, on which tag of which repository, recorded that digest — but the tarball carries no signature of its own, the node's install path (an operator's; `install.sh` installs the runtime only, and does run the verifier — [install.md](install.md) §1) runs the verifier only by hand, releases before the signing step (v0.4.1 and earlier) have no bundle, and the image takes the node from the tarball by checksum when built from a release (`image/Containerfile`'s release stage) and compiles it, unsigned, when built from a checkout. | A deployment that verifies the manifest by hand gets the node's publisher/workflow identity; one that only checks the `.sha256` gets integrity alone. The protocol window it gets is the one in the release's source commit (compatibility.md §6). | Download the tarball, its `.sha256`, and the release's manifest with its `.sha256` and `.sigstore.json`; run `scripts/release/verify-manifest.sh <manifest> <bundle> --tag <tag>` beside them and proceed only on `state=provenance-verified`; check that `ward-node --version` prints the release version, and record the release beside the deployment (node-integration-guide.md §1). | [#148](https://github.com/hexrift/WardOS/issues/148) (ADR-0028: tarball signing, install-path verification); a node version of its own is [#275](https://github.com/hexrift/WardOS/issues/275) |

## 4. What this means for a control plane

Read together, the rows above give the honest integration shape of node-integration.md
§11.5: bounded, snapshot-based actions and verification runs, offline unless the operator
enabled the allowlist, returning a declared, bounded result when the operator enabled
that, driven from the node's host by a client the control plane trusts or from elsewhere
over mutual TLS with certificates the operator provisions, with the receipt
read from `inspect`, the result read from `result` and the proof read from the evidence
log on the host, calling an authenticated HTTP service only through a credential the
node brokers when the operator configured it, reaching a held host or credential only
once the control plane approved it, and running an agent adapter the operator hosts under
exactly the authority its manifest grants, whichever adapter it is, its command hooks and
model route, and any workload's stock HTTP clients, working under the operator's shim. A
control plane that needs more (credentials in the workload's own hands, streamed output or a workspace export, approvals the node enforces on anything but a held host or credential, enrolment,
attestation, certificate revocation lists or revocation that reaches every node) is waiting on the issues named here, and should fail closed rather than
approximate them: do not grant what the node cannot enforce, do not infer success from
`unknown`, and do not carry a result the node never returned.
